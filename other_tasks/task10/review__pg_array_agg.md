# Ревью расширения pg_array_agg

## Общая информация

### Сборка и тестирование

Расширение корректно собирается и с использованием `PGXS`, и без него, т.е. при добавлении в директорию `contrib/` исходных файлов. В обоих случаях `make` выполняется без предупреждений, тесты проходят. Покрытие тестами хорошее.

### Структура документа

Каждая отдельная заметка пронумерована в соответствии со следующим шаблоном:

#### `F1`.`01`.`01`

1. Первые два символа указывают на принадлежность заметки разделу, здесь:
   - `D1` - ошибка / несоответствие в дизайн-документе (файл `README.md`);
   - `F1` - ошибка в реализации основных функций, описанных в файле `pg_array_agg.c`;
   - `F2` - ошибка в реализации вспомогательных функций, описанных в файле `utilfunc.c`;
   - `F3` - ошибки в файле `utilfunc.h`;
   - `G1` - общие для кода ошибки / неточности / замечания;
2. Следующее после точки число показывает подраздел:
   - `01` - критические ошибки - утечки памяти, несоответствие документации действительности и т.д.;
   - `02` - риски и менее важные неточности:
     - в разделах `F`: антипаттерны и "технический долг" - ситуации, когда код корректно работает, однако в будущем может привести к проблемам / замедлению разработки;
     - в разделе `D1`: вопросы к неочевидным архитектурным решениям, некорректные формулировки;
   - `03` - рекомендации по стилю кода (например, названия макросов) и минорные ошибки в оформлении (например, опечатки);
3. Последнее число - порядковый номер заметки в разделе.

### Общие замечания

---

#### G1.03.01

---

<p>Общее оформление кода:</p>

```C
/* Рассматриваются конструкции следующего вида: */
int func(void) {
    int a, b;
    if / while / for ( /* ... */ ) {
        /* ... */
    }
}
```

<p>Комментарий:</p>

В PostgreSQL неофициально принято после декларации переменных добавлять пустую строку, а также после определения функций, после if, while и т.д. фигурная скобка ставится на новой строке. В коде везде конструкции оформлены как в примере выше, лучше так:

```C
int func(void) 
{
    int a, b;
    
    if / while / for ( /* ... */ ) 
    {
        /* ... */
    }
}
```

*(Примечание: напиши мне по поводу этого замечания, скажу, откуда конкретно я взял эту информацию)*

## Реализация основных функций

### Критические

#### F1.01.01

---

<p>Функции array_min и array_max</p>

```C
/* Отсутствие строки */ PG_FREE_IF_COPY(arr, 0); /* приводит к утечке памяти */
```

<p>Комментарий:</p>

Если `PG_GETARG_ARRAYTYPE_P(0)` сделал detoast-копию массива, происходит утечка памяти. Однако, ввиду того, что при типе массива `Numeric` возвращаемый элемент `Datum res` указывает внутрь массива, просто добавление `PG_FREE_IF_COPY(arr, 0);` приводит к ошибке **use-after-free** при возврате из функции (`PG_RETURN_NUMERIC(final_res);`). Таким образом, чтобы избежать утечки в любом случае, рекомендую сделать следующее:

```C
bool typbyval;
    int16 typlen;
    Datum result_copy;

    get_typlenbyval(arr->elemtype, &typlen, &typbyval);
    
    /* Цикл while */
    
    final_res = datumCopy(res, typbyval, typlen);
    PG_FREE_IF_COPY(arr, 0);
    array_free_iterator(arr_it);
    
    /* ... */
    
    PG_RETURN_NUMERIC(final_res);
}
```

```C
#define ARRAY_SIZE(arr) (sizeof(arr) / sizeof((arr)[0]))
```

Вообще, достаточно простого решения, т.к. вряд ли состав поддерживаемых типов будет меняться часто, но сам по себе макрос ARRAY_SIZE тоже довольно полезен.

#### F2.01.01

---

<p>Строки 52-53, функция UInt64GetNumeric:</p>

```C
char uint_buf[20] = {0};
sprintf(uint_buf, UINT64_FORMAT, num);
```

<p>Комментарий:</p>

Максимальное значение uint64 = 18446744073709551615, это 20 знаков. Для C-строки нужен ещё один знак - двоичный ноль `\0`. Таким образом, при записи двадцатизначного числа в `uint_buf` произойдет переполнение буфера - **UB**. Я вижу два достаточно простых решения:

- Можно просто увеличить буфер на 1:

```C
char uint_buf[21] = {0};
```

- Можно увеличить буфер сильнее и использовать `snprintf`:

```C
char uint_buf[32];
int len;

len = snprintf(uint_buf, sizeof(uint_buf), UINT64_FORMAT, num);
if (len < 0 || len >= (int) sizeof(uint_buf))
    ereport(ERROR,
            (errcode(ERRCODE_INTERNAL_ERROR),
             errmsg("UInt64GetNumeric: buffer overflow")));
```

### Риски и неоднозначность

#### F3.02.01

---

<p>Строки 21-29 и 55-59:</p>

```C
typedef struct {
   PredicateType predicate_type;
   Operator op;
   char* const1;
   char* const2;

   int32 const1len;
   int32 const2len;
} ParsedPredicate;

/* ... */

typedef struct {
    TokenType type;
    const char* token; // указатель на начало подстроки
    int32 lenght; // длина подстроки
} Token;
```

<p>Комментарий:</p>

В синтаксическом анализе используются строки наподобие этой, в них строка токена приводится к `char *`:

```C
predicate->const1 = (char *) parsed_tokens[const1pos].token;
```

При этом само поле `token` является константным **указателем внутрь** предикатной строки, и в лексическом анализе инициализируется именно так. Таким образом, теоретически возможная в этом случае запись в поле `const1` или `const2` (например, `predicate->const1 = "smth"`) приводит к **UB**. Для решения этой проблемы я предлагаю сделать `const char *` поля `const1` и `const2` и убрать приведение к `char *` из строк синтаксического анализа. На функциональность это повлиять не должно, но закроет возможное UB.


Весь код после `ereport` по сути мёртвый, т.к. `ereport` не возвращает управление. На исполнение не влияет никак, но можно удалить.

## Заключение
